Bagian 02

Access Control

Metode pembatasan akses user ke resources organisasi — menjaga confidentiality, integrity, dan availability informasi.

Access control adalah metode pembatasan akses user ke resources organisasi. Aspek krusial dari implementasi access control adalah menjaga integrity, confidentiality, dan availability informasi. Fungsi access control menggunakan mekanisme identifikasi, autentikasi, dan otorisasi untuk mengidentifikasi, mengautentikasi, dan mengotorisasi user yang request akses ke resource spesifik. Access permissions menentukan approval atau permission yang diberikan ke user untuk mengakses sistem dan resources lain.

Access Control Mechanism — 4 Langkah
Gambar 3. Access control mechanism 4 langkah — Identify → Authenticate → Grant → Authorize. Setiap langkah adalah trust boundary.

Langkah-langkah umum yang terlibat dalam mekanisme access control adalah sebagai berikut: (1) User memberikan credentials/identifikasi saat login ke sistem. (2) Sistem memvalidasi user dengan database berdasarkan credentials/identifikasi yang diberikan seperti password, fingerprint, dll. (3) Setelah identifikasi berhasil, sistem memberikan user akses untuk menggunakan sistem. (4) Sistem kemudian mengizinkan user melakukan hanya operasi atau mengakses hanya resources yang telah diotorisasi.

Insight Penting: Access control adalah implementation of CIA Triad — Confidentiality (only authorized access), Integrity (only authorized modification), Availability (resources accessible when needed). Tanpa access control yang tepat, ketiga prinsip IA tidak dapat dijamin.
Bagian 03

Access Control Terminologies

Lima terminologi inti yang mendefinisikan access control pada resources spesifik.

Berikut adalah terminologi yang digunakan untuk mendefinisikan access control pada resources spesifik. Memahami terminologi ini penting karena semua dokumentasi security, audit report, dan framework compliance (NIST, ISO 27001) menggunakan istilah-istilah ini secara konsisten.

5 Terminologi Access Control — Subject ↔ Object via Reference Monitor
Gambar 4. 5 terminologi access control — Subject request → Reference Monitor validates → Object allow/deny. Operation = action yang dilakukan.
Subject
Subject dapat didefinisikan sebagai user atau process yang mencoba mengakses objects. Subject adalah entitas yang melakukan tindakan tertentu pada sistem. Contoh: user (Alice, Bob), service account (web-app-svc), process (cron job, daemon).
Object
Object adalah explicit resource di mana access restriction diterapkan. Access control yang diimplementasikan pada objects mengontrol tindakan yang dilakukan user. Contoh object: file, hardware device, database record, network share, API endpoint.
Reference Monitor
Reference monitor memantau restrictions yang diterapkan berdasarkan aturan access control tertentu. Reference monitor mengimplementasikan set aturan pada kemampuan subject untuk melakukan tindakan tertentu pada object. Ini adalah "gatekeeper" yang mengevaluasi setiap akses request.
Operation
Operation adalah action yang dilakukan oleh subject pada object. User yang mencoba menghapus file adalah contoh operation. Di sini, user adalah subject, action menghapus = operation, dan file = object. Operasi umum: read, write, execute, delete, modify, append.
Access Permission
Access permissions menentukan approval atau permission yang diberikan ke user untuk mengakses sistem dan resources lain. Permissions dikategorikan sebagai read, write, execute, delete, modify — atau lebih granular seperti read-only specific fields di database.
Bagian 04

Access Control Principles

Tiga prinsip yang menjelaskan level permission user secara detail — SoD, Need-to-know, POLP.

Prinsip access control menjelaskan level permission user secara detail. Dengan mengimplementasikan proses access control, keamanan processes dan resources dapat dipastikan. Proses access control harus didasarkan pada prinsip-prinsip berikut.

3 Prinsip Access Control — SoD → Need-to-know → POLP
Gambar 5. 3 prinsip access control — SoD (process) → Need-to-know (information) → POLP (granular task). POLP adalah yang paling ketat.
🔀
Separation of Duties (SoD)

SoD melibatkan breakdown authorization process menjadi berbagai steps. Privileges berbeda ditugaskan ke subject yang berbeda di setiap step. Memastikan tidak ada single individual yang memiliki authorization rights untuk melakukan semua fungsi. Contoh: developer tidak boleh deploy ke produksi sendiri; yang deploy beda orang.

🎯
Need-to-know

Di bawah prinsip need-to-know, akses diberikan hanya ke informasi yang diperlukan untuk melakukan tugas spesifik. Contoh: analyst keuangan tidak perlu akses ke source code; software engineer tidak perlu akses ke data pelanggan.

⚠
Principle of Least Privilege (POLP)

POLP memperluas need-to-know dalam memberikan akses ke sistem. POLP memberikan employee exactly the need-to-know level — tidak lebih, tidak kurang. Membantu organisasi dari malicious behavior, meningkatkan system stability dan security. Dua sub-prinsip: low rights & low risks.

Best Practice Implementasi: POLP adalah gold standard di cloud-native era. Implementasi via: (1) just-in-time (JIT) access — grant permission saat dibutuhkan, revoke setelah selesai; (2) role-based access — permission attached ke role, bukan ke user; (3) permission review quarterly — audit siapa punya akses ke apa; (4) zero-standing-privilege — tidak ada admin permanent, semua via PAM (Privileged Access Management).
Bagian 05

4 Access Control Models

Empat model access control — MAC, DAC, RBAC, RB-RBAC — yang menyediakan framework untuk implementasi.

Access control models adalah standar yang menyediakan framework predefined untuk mengimplementasikan level access control yang diperlukan. Access control models menentukan bagaimana subject dapat mengakses object. Pemilihan model yang tepat bergantung pada sensitivitas data, kompleksitas organisasi, dan kebutuhan compliance.

4 Model Access Control — Perbandingan
Gambar 6. 4 model access control — MAC (paling ketat, military) → DAC (fleksibel, owner-based) → RBAC (role-based, enterprise) → RB-RBAC (dynamic, modern cloud).

5.1 Detail Setiap Model

M
Mandatory Access Control (MAC)

MAC menentukan usage dan access policies untuk user. User dapat akses resource hanya jika punya access rights. MAC diaplikasikan untuk data yang ditandai highly confidential. Administrator menerapkan MAC tergantung OS dan security kernel. Tidak mengizinkan end-user memutuskan siapa yang bisa akses informasi. Contoh: SELinux, Trusted Solaris.

D
Discretionary Access Control (DAC)

DAC menentukan access control yang diambil oleh pemilik object untuk memutuskan access control subject ke object tersebut. DAC alternatif disebut need-to-know access model. Keputusan owner bergantung pada: file/data ownership (menentukan access policies user) & access rights/permissions (owner set access privileges ke subject lain). Contoh: UNIX, Linux, Windows ACL.

R
Role-Based Access Control (RBAC)

Di RBAC, access permissions tersedia berdasarkan access policies yang ditentukan sistem. Permissions di luar kontrol user — user tidak dapat amend access policies yang dibuat sistem. 3 aturan: role assignment, role authorization, transaction authorization. Sangat scalable untuk enterprise besar dengan ribuan user.

R
Rule-Based Access Control (RB-RBAC)

Permissions ditugaskan ke user role dynamic berdasarkan set of rules yang didefinisikan administrator. Rules dapat berbasis: waktu (jam kerja), lokasi (IP geolocation), context (device posture), risk (anomali detection). Ini adalah evolusi RBAC untuk era cloud dan zero-trust.

Aturan Praktis Pemilihan Model: MAC untuk military/intelligence (data sangat sensitif, per-label classification). DAC untuk file sharing kolaboratif (user kontrol own files). RBAC untuk enterprise standard (organisasi dengan struktur role jelas). RB-RBAC untuk modern cloud + zero-trust (akses dinamis berbasis context). Kombinasi sering digunakan — RBAC sebagai dasar, RB-RBAC sebagai override.
Bagian 06

Implementasi Logical di Windows OS

Contoh konkret implementasi MAC, DAC, RBAC di Windows: UAC, File Permissions, JEA, WAC.

Implementasi logical MAC, DAC, dan RBAC dapat ditemukan di Windows operating system. Windows menyediakan berbagai fitur yang mengimplementasikan ketiga model access control ini secara native — sebagai contoh konkret bagaimana teori diterjemahkan ke produk nyata.

🛡
MAC: User Account Control (UAC)

Di Windows OS, fitur User Account Control (UAC) mengimplementasikan MAC security model. UAC membatasi instalasi application software hanya melalui administrator authorizations. User tanpa administrative privileges dibatasi untuk install aplikasi apapun di sistem. Saat ada request install, UAC memunculkan prompt yang memerlukan admin consent.

MACWindows native
📁
DAC: Windows File Permissions

Di Windows OS, DAC diimplementasikan untuk assigning file permissions ke groups/users spesifik. Permissions untuk akses files & folders di sistem, akses files di old account user, atau edit system files — semua dikontrol menggunakan DAC. Owner file dapat grant/deny access ke user lain.

DACACL-based
⚙
RBAC: Just Enough Administration (JEA)

Just Enough Administration (JEA) management framework di Windows mengimplementasikan RBAC untuk membatasi hak IT administrators di remote PowerShell sessions. Menggunakan JEA, fine-grained access control dapat diimplementasikan untuk non-administrators menjalankan specific commands, scripts, dan executables tanpa full admin rights.

RBACPowerShell
🖥
RBAC: Windows Admin Center (WAC)

Windows Admin Center (WAC) adalah tool yang membantu konfigurasi RBAC untuk managing server. Konsep role di WAC berbasis JEA, yang memungkinkan granting required rights ke non-administrators. WAC memberikan unified portal untuk manage Windows Server, Windows Client, dan cluster.

RBACWeb-based
Implementasi di Linux: Setara dengan Windows, Linux juga mengimplementasikan ketiga model: MAC via SELinux (Red Hat/CentOS) atau AppArmor (Ubuntu/Debian); DAC via file permissions (chmod/chown) dan POSIX ACL; RBAC via sudoers file dan Linux capabilities. Pemahaman cross-platform penting untuk security engineer yang bekerja di environment hybrid.
Bagian 07

Identity and Access Management (IAM)

Kerangka kerja yang memastikan right individual dapat right access di right time.

Identity and Access Management (IAM) bertanggung jawab untuk memberikan right individual dengan right access di right time. IAM menawarkan role-based access control ke customer atau employee organisasi untuk mengakses informasi kritis dalam enterprise. IAM terdiri dari business processes, policies, dan technologies yang memungkinkan monitoring electronic atau digital identities.

Produk IAM menyediakan system administrator dengan tools dan technologies untuk mengatur user access (create, manage, remove access) ke sistem atau jaringan berdasarkan roles individual user dalam enterprise. Organisasi umumnya memilih all-in-one authentication implementation yang dapat diperluas ke identity federation — karena identity federation mencakup IAM dengan Single Sign-On (SSO) dan centralized Active Directory (AD) account untuk management yang aman.

IAM Framework — 4 Area Fungsional
Gambar 7. IAM Framework 4 area — Authentication, Authorization, User Management, Central User Repository. Semua komponen IAM dikelompokkan di 4 area ini.

Organisasi harus memastikan correctness of data untuk functioning IAM yang tepat. IAM framework dapat dibagi menjadi empat area: authentication, authorization, user management, dan central user repository. Semua komponen IAM dikelompokkan di bawah empat area ini.

Key responsibility dari Identity Management (IDM) framework adalah mengelola shared identity repository yang diakses oleh applications dan access management system.

IAM di Era Cloud: IAM modern bergeser dari on-prem AD ke cloud-based identity provider (IdP): Okta, Azure AD (Entra ID), Google Workspace, Auth0, Keycloak. Cloud IdP mendukung federation (SAML, OAuth 2.0, OIDC), SSO cross-domain, dan adaptive MFA. Tren terbaru: Identity as a Service (IDaaS) dan Zero Trust Architecture di mana identity menjadi perimeter utama.
Bagian 08

User Identity Management (IDM)

Konfirmasi identitas user, process, atau device yang mengakses jaringan.

Identification berkaitan dengan konfirmasi identitas user, process, atau device yang mengakses jaringan. User identification adalah teknik yang paling umum digunakan untuk mengautentikasi user di jaringan dan aplikasi. User memiliki unique user ID yang membantu identifikasi mereka.

Identity Management melibatkan penyimpanan dan pengelolaan user attributes di repository mereka. Di sini, user repository adalah database di mana attributes terkait identitas user disimpan. Process autentikasi termasuk verifikasi user ID dan password. User diharuskan memberikan kedua credentials untuk mendapatkan akses ke jaringan.

🆔
Identification

Konfirmasi identitas user, process, atau device yang mengakses jaringan. User identification adalah teknik paling umum untuk autentikasi user. Setiap user punya unique user ID untuk identifikasi.

🗄
User Repository

Database tempat attributes identitas user disimpan. Contoh: Active Directory, LDAP directory, Okta Universal Directory, Azure AD. Berisi: username, email, role, department, manager.

🔑
Authentication Process

Verifikasi user ID dan password. User harus memberikan kedua credentials untuk mendapat akses. Network administrator memberikan access controls (username, account number) dan permissions ke services lain berdasarkan user IDs.

👤
User Attributes

Data yang disimpan per user: username, full name, email, role, department, manager, location, employee ID, hire date, security group memberships. Attributes ini yang dipakai RBAC untuk assign permissions.

Identity Lifecycle: IDM mengelola identitas dari joiner (onboarding) → mover (role change, transfer) → leaver (offboarding). Setiap fase memerlukan automation: joiner = auto-provisioning dari HR system, mover = role reassignment, leaver = auto-deprovisioning semua akses. Manual process = error & orphan accounts.
Bagian 09

3 Faktor Autentikasi

Something you know, something you have, something you are — pondasi multi-factor authentication.

Authentication melibatkan verifikasi credentials yang diberikan user saat mencoba connect ke jaringan. Baik jaringan wired maupun wireless melakukan autentikasi user sebelum mengizinkan mereka mengakses resources di jaringan. User authentication khas terdiri dari user ID dan password. Bentuk autentikasi lain termasuk mengautentikasi website menggunakan digital certificate dan membandingkan produk dengan label yang terkait.

3 Faktor Autentikasi — Know × Have × Are
Gambar 8. 3 faktor autentikasi — Know × Have × Are. Kombinasi 2+ faktor = MFA yang sulit di-bypass.

Faktor yang terkait dengan process autentikasi adalah sebagai berikut: (1) Something you know — user harus tahu informasi seperti username, password, dll. saat login ke sistem atau jaringan. (2) Something you have — user harus memegang informasi seperti one-time password token, employee ID card, dll. saat login. (3) Something you are — user harus menggunakan karakteristik biometric seperti retina scan, fingerprint scan, dll. saat login.

Best Practice: MFA modern menggunakan adaptive/risk-based approach — minta faktor tambahan hanya saat risk tinggi (login dari device baru, lokasi unusual, jam aneh). Ini menyeimbangkan security vs user experience. Contoh: Google Prompt, Microsoft Authenticator number matching, FIDO2/WebAuthn security key.
Bagian 10

Password Authentication

Metode autentikasi paling umum — dengan kelebihan simplicity dan kekurangan kerentanan terhadap brute force dan dictionary attacks.

Dalam password authentication, user diharuskan memberikan username dan password untuk membuktikan identitas mereka ke sistem, aplikasi, atau jaringan. Credentials kemudian dicocokkan dengan daftar authorized users di database/Windows AD. Setelah match, user dapat mengakses sistem.

User password harus mengikuti standard password creation practices, termasuk campuran alphabets, numbers, dan special characters serta panjang lebih dari 8 karakter (karena password kecil mudah ditebak).

✓
Kelebihan Password

• Simple — tidak butuh hardware khusus
• Universal — didukung semua sistem
• Low cost — tidak ada biaya token/smart card
• User familiar — sudah terbiasa semua user
• Easy implement — developer-friendly

⚠
Kerentanan Password

Password authentication rentan terhadap:
• Brute force attacks — coba semua kombinasi karakter
• Dictionary attacks — coba word list umum
• Packet sniffing — capture plaintext di jaringan
• Phishing — social engineering credential theft
• Credential stuffing — reuse password dari breach lain

10.1 Password Best Practices (NIST SP 800-63B)

📏
Length & Complexity

Minimum 12 karakter (NIST 800-63B 2017+). Tidak wajib complexity rules kaku (huruf besar/kecil/angka/simbol) — yang penting length. Passphrase panjang lebih baik dari password pendek kompleks. Contoh: correct-horse-battery-staple lebih kuat dari P@ssw0rd!.

🚫
Forbidden Practices

JANGAN: (1) pakai password default, (2) reuse password antar akun, (3) pakai info personal (nama, tanggal lahir), (4) tulis password di sticky note, (5) share password via email/chat, (6) require regular rotation (NIST 2017 — rotation justru menurunkan security).

🔐
Storage & Hashing

Store password sebagai hash dengan salt unique per user. Algoritma: Argon2 (modern, winner Password Hashing Competition 2015), bcrypt (industri standard), scrypt, PBKDF2 (legacy). JANGAN pakai MD5, SHA-1 (tanpa salt) — sudah broken untuk password.

🛡
Breach Protection

Cek password terhadap breach databases (HaveIBeenPwned API, k-anonymity). Block password yang muncul di breach umum. Implementasi rate limiting (max 5 attempts/15 menit) dan account lockout setelah 10 failed attempts.

Realitas 2024: 81% breach melibatkan password lemah/curi (Verizon DBIR). Password saja tidak cukup untuk data sensitif. Minimum MFA wajib untuk: email, banking, social media, remote access (VPN/SSH), admin accounts. Tren: passwordless authentication via FIDO2/WebAuthn — biometric + device crypto key, tanpa password sama sekali.
Bagian 11

Smart Card Authentication

Teknologi kartu pintar dengan microchip untuk autentikasi yang lebih kuat dari password.

Organisasi menggunakan smart card technology untuk memastikan autentikasi yang kuat. Smart card dapat menyimpan password files, authentication tokens, one-time password files, biometric templates, dll. Teknologi ini digunakan dengan authentication token lain, sehingga memberikan multi-factor authentication. Ini memungkinkan logical access security yang efisien.

💳
What is Smart Card?

Smart card terdiri dari small computer chip yang menyimpan personal information user untuk identifikasi. Kartu dimasukkan ke machine untuk autentikasi, dan PIN diinput untuk memproses informasi autentikasi di kartu. Smart card juga membantu menyimpan public dan private keys.

🔐
Cryptography-Based

Smart card authentication adalah teknik cryptography-based yang memberikan security lebih kuat dari password authentication. Keuntungan utama: eliminates risk credential theft dari computer karena credentials disimpan di chip kartu — bukan di komputer yang bisa di-malware.

11.1 Use Case Smart Card

🌐
VPN Authentication

Smart card sebagai VPN client certificate — autentikasi ke VPN gateway lebih aman dari password.

📧
Email & Data Encryption

Simpan private key PGP/S-MIME di smart card — email decrypt hanya bisa di kartu fisik.

✍
Electronic Signatures

Digital signature via smart card — non-repudiation kuat untuk dokumen legal.

📶
Secure Wireless Logon

802.1X EAP-TLS dengan smart card certificate — WPA2-Enterprise authentication.

👤
Biometric Authentication

Simpan biometric template di smart card — match local di kartu, tidak transit data biometric.

🏛
Government / eID

e-KTP Indonesia, eIDAS EU, US PIV card — identitas digital government berbasis smart card.

11.2 Kelebihan & Kekurangan Smart Card

✓Kelebihan

  • Highly secure technology — efficient encryption & authentication
  • Easy to carry — user hanya perlu tahu PIN kartu
  • Reduced deception — simpan biometric, recognize employees
  • Credential theft resistant (chip tamper-resistant)
  • Multi-purpose (VPN, email, signature, Wi-Fi)
  • Standar PKCS#11 untuk interoperabilitas

−Kekurangan

  • Easily lost — ukuran kecil, mudah hilang
  • Security risk jika hilang — info & identity owner berisiko
  • High production cost — microchip + encryption tech = mahal
  • Limited storage di microchip
  • Butuh reader hardware di setiap endpoint
  • Replacement lambat — issue kartu fisik baru
Era Passwordless: Smart card berevolusi menjadi FIDO2 security keys (YubiKey, Google Titan) yang lebih praktis — USB/NFC, no reader khusus, support WebAuthn. Apple/Google/Apple Microsoft mendukung passkeys (FIDO2 credential tersinkron antar device) sebagai penerus smart card untuk consumer.
Bagian 12

Biometric Authentication

Teknologi identifikasi karakteristik manusia — 6 jenis utama dengan kelebihan & risiko unik.

Biometrics adalah teknologi yang mengidentifikasi karakteristik manusia untuk mengautentikasi orang. Biometric paling umum digunakan adalah fingerprint scanner, retina scanner, facial recognition, DNA, dan voice recognition. Biometric authentication melibatkan 3 langkah: (1) Reader memindai biometric data. (2) Software mengubah informasi yang dipindai menjadi digital form dan membandingkannya dengan biometric data yang tersimpan di database. (3) Jika kedua data cocok, konfirmasi autentisitas user dan izinkan permission.

6 Jenis Biometric Authentication
Gambar 9. 6 jenis biometric authentication — fingerprint (umum) hingga vein structure (high-security). Setiap jenis punya trade-off accuracy vs convenience.
Kasus Nyata: Clearview AI (2020) mengumpulkan 30+ milyar foto dari social media untuk face recognition tanpa consent. Apple Face ID (2017) — 1 dari 1 juta false positive, tetapi rentan twin/sibling. Pay-by-face di China (Alipay) — convenience tinggi tapi surveillance concern. Pelajaran: biometric perlu regulasi ketat (GDPR Article 9 special category data, UU PDP Indonesia).
Bagian 13

Two-Factor Authentication (2FA) & MFA

Kombinasi 2+ faktor autentikasi yang menurunkan identity theft dan phishing secara signifikan.

Two-factor authentication adalah proses di mana sistem mengkonfirmasi identifikasi user dalam dua step. User dapat menggunakan physical entity seperti security token sebagai salah satu credential dan credential lain dapat berupa security codes.

Two-factor authentication bergantung pada tiga faktor: something you have, something you know, something you are. Faktor "Something you are" adalah best companion dari two-factor authentication karena dianggap paling sulit dipalsukan atau di-spoof.

2FA Combinations — 5 Kombinasi Umum
Gambar 10. 5 kombinasi 2FA — dari Password+SmartCard hingga Tokenless. Tokenless paling praktis untuk deployment massal.
✓
Kelebihan 2FA/MFA

• Menurunkan identity theft & phishing secara signifikan
• Password bocor saja tidak cukup untuk login
• Compliance ke regulasi (PCI DSS, HIPAA, GDPR)
• Adaptive — bisa step-up only saat risk tinggi
• User-friendly (tokenless via app)

−
Kekurangan 2FA/MFA

• Delay — user harus tunggu organisation issue physical token
• User friction — step ekstra di setiap login
• Cost — hardware token mahal
• Recovery complex — kehilangan token = lockout
• SIM swap attack — SMS OTP rentan

Standar MFA Modern: FIDO2/WebAuthn (2019) — standar passwordless berbasis public key cryptography. User authentic via biometric/PIN ke device (laptop, smartphone, security key), device sign challenge dengan private key, server verify dengan public key. Tidak ada password yang transit jaringan. Didukung Google, Microsoft, Apple, Amazon — adalah masa depan MFA.
Bagian 14

Single Sign-On (SSO) Authentication

Satu username dan password untuk akses multiple aplikasi — dengan trade-off security vs convenience.

Sesuai namanya, SSO memungkinkan user mengakses multiple aplikasi menggunakan single username dan password. SSO menyimpan credentials user di SSO policy server. Contoh SSO adalah Google applications — user dapat mengakses semua Google apps (Gmail, Drive, YouTube, Calendar) menggunakan single username dan password.

SSO Workflow — Cookie-based Session Management
Gambar 11. SSO workflow — user login sekali ke SSO server, dapat cookie + token, lalu access multiple apps tanpa re-login.

Central service (Google, dll.) membuat cookie untuk semua user yang login pertama kali di aplikasi manapun. Saat user mencoba mengakses aplikasi lain dari central service, kebutuhan untuk memasukkan credentials lagi tereliminasi karena cookie yang sudah dibuat. Sistem memeriksa credentials menggunakan cookie yang dibuat.

14.1 Kelebihan & Kekurangan SSO

✓Kelebihan SSO

  • Reduces re-authentication → meningkatkan produktivitas
  • Removes phishing chances — satu titik login
  • Better application management — centralized database
  • Account lifecycle assist — provisioning/deprovisioning simplified
  • No need remember multiple passwords
  • Reduces time memasukkan username/password
  • Audit trail central — semua login di satu log

−Kekurangan SSO

  • Losing credentials = high impact — semua apps unavailable
  • Single point of failure — SSO down = semua apps down
  • Vulnerability issues — auth semua apps terkait
  • Multi-user computer issue — butuh security policy
  • Cookie hijacking — jika cookie dicuri, semua apps compromised
  • Session fixation — attack pada session ID
  • Vendor lock-in — migrasi SSO provider rumit

14.2 Protokol SSO Modern

S
SAML 2.0

Security Assertion Markup Language — XML-based, dominan di enterprise. IdP (Identity Provider) issue assertion ke SP (Service Provider). Cocok untuk web SSO enterprise (Salesforce, Office 365, Workday).

O
OAuth 2.0

Open Authorization — framework untuk delegated access. User authorize app pihak ketiga mengakses resource tanpa share password. Cocok untuk API access (Login with Google/Facebook).

O
OpenID Connect (OIDC)

Layer autentikasi di atas OAuth 2.0 — JSON/REST based, modern. Mendukung ID token (JWT) yang berisi identity claims. Cocok untuk mobile + SPA (Single Page Application).

Trade-off SSO: SSO adalah double-edged sword. Convenience tinggi = risiko tinggi jika SSO server compromised. Mitigasi: (1) wajib MFA di SSO server, (2) short session timeout (8 jam), (3) step-up auth untuk aplikasi sensitif, (4) monitoring anomaly (login dari geolocation baru), (5) token revocation list untuk logout immediate.
Bagian 15

Authorization — 4 Types

Empat bentuk otorisasi: Centralized, Decentralized, Implicit, Explicit — masing-masing dengan trade-off.

Authorization merujuk pada proses memberikan permission untuk mengakses resources atau melakukan action di jaringan. Administrator dapat memutuskan user privileges dan access permissions user di sistem multi-user. Mekanisme otorisasi memungkinkan administrator membuat access permissions untuk user serta memverifikasi access permissions yang dibuat untuk setiap user. Otorisasi dapat mengambil bentuk berbeda berdasarkan kebutuhan organisasi.

4 Tipe Authorization — Decision Matrix
Gambar 12. 4 tipe authorization — Centralized/Decentralized (database) × Implicit/Explicit (access pattern).

15.1 Detail Setiap Tipe

Centralized Authorization
Kebutuhan centralized authentication muncul saat sulit mengimplementasikan otorisasi individual per resource. Menggunakan central authorization database yang mengizinkan/menolak akses user — keputusan akses bergantung pada policies yang dibuat unit terpusat. Memudahkan otorisasi user mengakses platform berbeda. Easy to handle, low cost, single database untuk semua aplikasi. Contoh: Active Directory, Okta, Azure AD.
Decentralized Authorization
Decentralized authorization memelihara separate database per resource. Database berisi detail semua user yang diizinkan mengakses resource tertentu. Proses decentralized memungkinkan user memberikan akses ke user lain — meningkatkan fleksibilitas. Tapi: cascading & cyclic authorizations menjadi isu. Contoh: UNIX file permissions, wiki access control, per-database grants di PostgreSQL.
Implicit Authorization
Implicit authorization memberikan akses resources indirectly. Task dimungkinkan setelah user menerima otorisasi untuk primary resource yang melaluinya akses ke resource yang diminta dimungkinkan. Contoh: user yang request web page punya permission akses main page + semua pages linked. User mendapat indirect access ke links dan documents yang terattach. Higher granularity.
Explicit Authorization
Explicit authorization memelihara separate authorization details per resource request. Teknik ini lebih sederhana dari implicit. Tapi membutuhkan storage space besar untuk menyimpan semua authorization details. Cocok untuk system yang membutuhkan audit trail jelas per resource — misal microservices dengan per-endpoint permission.
Pemilihan Praktis: Centralized + Explicit = pilihan default untuk enterprise modern (mudah audit, konsisten). Decentralized + Implicit cocok untuk collaborative platform (wiki, file share). Hindari Decentralized + Implicit — kombinasi paling sulit diaudit dan paling rentan privilege escalation.
Bagian 16

User Accounting

Tracking who, when, dan how users mengakses jaringan — untuk trend analysis, breach detection, dan forensics.

User accounting melibatkan tracking tindakan yang dilakukan user di jaringan. Ini melacak who, when, dan how user mengakses jaringan. Termasuk verifikasi files yang diakses user dan fungsi seperti alterasi atau modifikasi files atau data. Membantu mengidentifikasi tindakan authorized dan unauthorized.

User Accounting — Tracking Flow & Use Cases
Gambar 13. User Accounting — tracking WHO/WHEN/HOW + 3 use cases (trend, breach detection, forensics). Bagian dari AAA.

Data accounting dapat digunakan untuk trend analysis, data breach detection, forensics investigations, dll. Accounting adalah "A" ketiga dari AAA (Authentication, Authorization, Accounting) — tanpa accounting, dua komponen lain tidak dapat diaudit dan diverifikasi.

16.1 Implementasi Accounting

📊
Logging Systems

Syslog (RFC 5424) — standar Unix logging. Windows Event Log — Security, Application, System logs. SIEM (Splunk, Elastic, QRadar) — agregasi + correlation + alerting. Auditd — Linux audit subsystem untuk syscall tracking.

🗄
Log Retention Policy

Regulasi menentukan minimum retention: PCI DSS = 1 year, HIPAA = 6 years, SOX = 7 years, UU PDP Indonesia = sesuai kebutuhan. Implementasi: hot storage (90 hari, search cepat) + cold storage (arsip, murah).

🚨
Real-time Alerting

Alert otomatis untuk: (1) login failed 5x dalam 5 menit, (2) login dari geo baru, (3) access sensitive resource di luar jam kerja, (4) mass data download, (5) privilege escalation attempt.

🔍
Forensic Readiness

Untuk forensics: log harus immutable (write-once, hash chain), time-synced (NTP), correlated (across systems), searchable (structured format). Tanpa ini, log tidak bisa jadi evidence di pengadilan.

Standar AAA: RADIUS (RFC 2865) — protokol AAA dominan untuk network access. TACACS+ — AAA untuk device administration (Cisco). Diameter — penerus RADIUS, lebih secure & scalable. Ketiganya mengimplementasikan Authentication + Authorization + Accounting sebagai satu kesatuan.

17.3 Workflow Praktikum 4 Sesi

Alur Praktikum — 4 Sesi, 20 Langkah, 1 Laporan Akhir
Gambar 14. Workflow 4 sesi praktikum Modul 02 — total 20 langkah hands-on.

17.4 Langkah Praktikum

Sesi 1 — Password Audit dengan John the Ripper

1
Install John the Ripper (Jumbo)

Build dari source untuk dapatkan semua format hash: git clone https://github.com/openwall/john && cd john/src && ./configure && make -j4. Atau install via package: apt install john. Verifikasi: john --list=formats — harus list ratusan format hash.

2
Generate Test Hash Set

Buat file hashes.txt dengan berbagai hash: openssl passwd -1 -salt xyz password123 (MD5 crypt), mkpasswd -m sha-512 -S salts StrongPass! (SHA-512). Tambahkan hash dari sample breach (rockyou.txt). Catat: algoritma hash, complexity password yang akan di-crack.

3
Dictionary Attack dengan rockyou.txt

Download rockyou.txt (14.3M passwords). Jalankan: john --wordlist=rockyou.txt hashes.txt. Tunggu 5-10 menit. Lihat hasil: john --show hashes.txt. Catat: password yang berhasil di-crack, waktu yang diperlukan, persentase sukses.

4
Brute Force & Rule-based Attack

Brute force 6-char: john --incremental=digits --max-length=6 hashes.txt. Rule-based (mutasi kata): john --wordlist=rockyou.txt --rules=KoreLogic hashes.txt. Bandingkan waktu dengan dictionary attack. Pelajari: mengapa passphrase 16+ char sulit di-crack.

5
Hashcat (GPU) & Laporan

Opsional jika ada GPU: hashcat -m 1800 -a 0 hashes.txt rockyou.txt (SHA-512 crypt). Bandingkan speed John vs Hashcat (CPU vs GPU). Buat laporan: (a) daftar password yang di-crack dengan waktu, (b) rekomendasi password policy, (c) berapa lama password 8/12/16 char dapat di-crack.

Sesi 2 — FreeRADIUS AAA Setup

1
Install FreeRADIUS + daloradius

Install: apt install freeradius freeradius-utils apache2 php php-mysql mariadb-server. Download daloradius dari GitHub, ekstrak ke /var/www/html/daloradius. Setup MySQL database radius, import schema. Konfigurasi /etc/freeradius/3.0/mods-available/sql untuk koneksi MySQL.

2
Konfigurasi Clients & Users

Edit /etc/freeradius/clients.conf — tambahkan NAS client (IP lab + secret). Via daloradius web UI (http://localhost/daloradius), tambahkan 5 user: admin (FR), user1-3 (regular), guest. Set attribute: Cleartext-Password, Reply-Message, Session-Timeout. Restart: systemctl restart freeradius.

3
Test Authentication dengan radtest

Test user valid: radtest user1 pass123 localhost 0 testing123 → harus Access-Accept. Test password salah: radtest user1 wrongpass localhost 0 testing123 → harus Access-Reject. Capture paket RADIUS dengan Wireshark (filter radius) — amati Access-Request, Access-Accept/Reject.

4
Configure Accounting

Enable accounting di /etc/freeradius/3.0/sites-available/default — bagian accounting. Login beberapa kali dengan user berbeda. Lihat accounting records di daloradius → "Accounting" tab. Amati: Acct-Status-Type (Start, Interim-Update, Stop), Acct-Session-Time, Acct-Input-Octets/Acct-Output-Octets.

5
Authorization Profiles & Laporan

Buat 3 profile: admin-profile (VLAN 10, full access), staff-profile (VLAN 20, restricted), guest-profile (VLAN 30, internet only). Assign ke user. Test dengan radtest + lihat atribut balasan. Laporan: (a) skema AAA, (b) capture RADIUS flow, (c) tabel user-profile, (d) accounting log sample.

Sesi 3 — Keycloak SSO Implementation

1
Install Keycloak

Download Keycloak dari keycloak.org. Run: ./bin/standalone.sh -b 0.0.0.0. Akses http://localhost:8080, login admin. Buat realm demo-realm. Buat 2 client: web-app-1 (OIDC) dan web-app-2 (SAML). Buat 3 user di realm: alice, bob, charlie dengan role berbeda.

2
Configure OIDC Client

Di client web-app-1, set Valid Redirect URIs = http://localhost:3000/*, Web Origins = http://localhost:3000. Catat client_id & client_secret. Setup sample Node.js/Python app dengan library OIDC (mis. python-oauthlib) yang redirect ke Keycloak untuk login.

3
Test SSO Flow

User akses web-app-1 → redirect ke Keycloak login → user input credentials → Keycloak issue ID token (JWT) + access token → redirect balik ke web-app-1 dengan token. Decode JWT di jwt.io — amati claims: sub, iss, aud, exp, email, role. Lalu akses web-app-2 — harus tanpa login ulang (SSO).

4
Configure MFA & SAML

Enable MFA di Keycloak: Authentication → OTP → Required Action. User alice setup Google Authenticator. Test login — setelah password, minta OTP. Lalu konfigurasi client web-app-2 sebagai SAML SP. Test SAML flow — amati SAML Assertion (XML) di Wireshark.

5
Audit Log & Laporan

Lihat Keycloak Events: login sukses, login failed, token refresh, logout. Laporan: (a) arsitektur SSO, (b) flow diagram OIDC + SAML, (c) sample JWT dengan decode, (d) MFA setup screenshot, (e) audit log events. Diskusikan: kelebihan/kekurangan SSO untuk enterprise.

Sesi 4 — MAC/DAC/RBAC Implementation Lab

1
DAC: Linux File Permissions

Buat 3 user: alice, bob, charlie. Buat file secret.txt sebagai alice. chmod 600 secret.txt — hanya owner. Test bob baca → Permission denied. Set ACL granular: setfacl -m u:bob:r secret.txt — bob bisa baca tapi tidak tulis. Lihat ACL: getfacl secret.txt. Pelajari: numeric vs symbolic permission.

2
RBAC: sudo Configuration

Edit /etc/sudoers via visudo. Buat rule: %webadmins ALL=(www) /usr/bin/systemctl restart apache2. Group webadmins hanya bisa restart Apache sebagai user www, tidak bisa command lain. Test: sudo -u www systemctl restart apache2 → sukses. Test command lain → ditolak. Pelajari: /etc/sudoers.d/ untuk modular config.

3
MAC: SELinux Modes

Cek mode: getenforce. Coba ubah: setenforce 0 (Permissive), setenforce 1 (Enforcing). Buat file di /var/www/html dengan context salah: mv /tmp/test.txt /var/www/html/. Lihat: ls -Z /var/www/html/test.txt — context tmp_t. Apache tidak bisa baca. Fix: restorecon /var/www/html/test.txt → context httpd_sys_content_t. Apache bisa baca.

4
Windows: UAC + File Permissions

Di Windows VM: buat user standard (non-admin). Coba install app → UAC prompt minta admin. Lalu klik kanu file → Properties → Security tab. Lihat ACL: user/group, permissions (Read, Write, Modify, Full Control). Tambah user baru dengan Read-only. Test akses. Pelajari: effective permissions calculation.

5
JEA: Just Enough Administration

Di Windows Server: install JEA. Buat role capability file: New-PSRoleCapabilityFile -Path .\WebAdmin.psrc — limit ke Restart-Service only. Buat session configuration: New-PSSessionConfigurationFile -Path .\JEA.pssc -RoleDefinitions .... Register: Register-PSSessionConfiguration -Name JEA -Path .\JEA.pssc. Test: user non-admin connect via Enter-PSSession -ComputerName localhost -ConfigurationName JEA. User hanya bisa run allowed commands.

Q4

POLP in Practice

  • SSO — cookie-based session, SAML 2.0 (enterprise XML), OAuth 2.0 (delegated access), OIDC (modern JSON/REST). Pro: convenience, con: single point of failure.
  • 4 tipe authorization — Centralized (single DB), Decentralized (per-resource), Implicit (indirect access), Explicit (per-request details).
